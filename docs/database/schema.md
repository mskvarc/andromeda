# Schema

Andromeda keeps context in a PostgreSQL schema built for NGSI-LD, not in a table of JSON documents. Names are interned into small dictionaries, an entity is a set of typed rows, the columns whose comparison decides API results fix their own collation, and history lives in a TimescaleDB hypertable. Each of these choices is there so that a request gets the same answer on any PostgreSQL server, and stays fast as a tenant grows.

## Databases

The database in `database.connection` is the platform database. It holds the tenant registry and the broker's own bookkeeping, such as maintenance state, and it's also the default tenant's database. Each named tenant gets a PostgreSQL database of its own, which the broker creates when the tenant first appears, as a copy of the tenant template that [Tenant template](#tenant-template) describes. Tenants share nothing, so one tenant's data, indexes and statistics never affect another's.

## Name dictionaries

The same attribute names and entity types repeat across millions of rows, and storing the full IRI on every row would bloat the tables every query reads. So each tenant has two dictionaries, `attribute_names` and `entity_type_names`, which give each expanded IRI an integer key, and every other table stores the key.

A dictionary only grows. A name gets its key the first time it's written and keeps it for the life of the tenant, and the database refuses to update or delete an entry. A write is never refused for bringing a new name. Each broker process caches the dictionaries within a memory budget, and a name missing from the cache costs one indexed read.

## Entities as typed rows

There is no stored entity document. An entity is spread over a few tables that share one entity key.

- `entities` holds identity and lifecycle, meaning the identifier, `createdAt`, `modifiedAt` and expiry. The same row serves the entity's current state and its Temporal Evolution.
- `entity_search` holds what queries search on, which is the entity's types, the names of its attributes, its Scopes and its `location`.
- `entity_type_members` has one row per type the entity has, marked as a type of its current state, of its Temporal Evolution, or of both.
- `current_attributes` has one row per attribute instance, that is, per entity, attribute name and `datasetId`.

An attribute instance keeps its value in exactly one typed column, chosen by the kind of value. The kinds include a number, a string, a boolean, a date-time, a date, a time, a geometry, a URI, and a structured value for anything that isn't a single scalar. A string or URI too long for a B-tree key goes to a long-text column of its own. Database constraints check that exactly one value column is filled and that it matches the kind. Numbers are PostgreSQL `numeric`, so they keep their exact value. Sub-attributes are stored with their instance, in the order they were written.

A data-integrity seal (clause 4.5.2.2) is the one sub-attribute with a value kind of its own, `data-integrity-proof`. Its W3C Data Integrity proof is in `value_proof`, a `data_integrity_proof` composite with a typed field for each member a proof must have, and its `entityIdSealed` and `entityTypeSealed` are in `seal_entity_id` and `seal_entity_type_keys` beside it. Any further member of the proof stays in the structured value encoding. The proof's `created` keeps the number of fractional-second digits it was written with, because a signature covers the literal as written. No row of `current_attributes` or `attribute_history` holds a seal, since a seal always signs the attribute it belongs to. A `q` filter or an ordering reads a seal's value through the SQL function `sub_attribute_value_object`, which rebuilds the expanded proof the model writes, so a seal compares like any other structured value. [Data-integrity seals](../data-integrity-seals.md) describes the model.

A read puts the entity back together from these rows, and the history and the notification queues hold instances in the same typed form. That's why a `q` filter compares numbers as numbers and date-times as instants, and why a value reads back as it was validated.

Deleting an entity (clauses 5.6.6 and 5.6.10) removes its current state but not its history, which only Delete Temporal Evolution (clause 5.6.16) removes. An entity with a Temporal Evolution therefore keeps its `entities` row, with `createdAt`, `modifiedAt` and expiry cleared, and keeps its `entity_type_members` rows marked as types of the Temporal Evolution only. Its `entity_search` and `current_attributes` rows go in the same transaction. Core API reads select only current-state members, and type discovery counts from census tables that every write of the search rows keeps up to date in the same statement, so the entity is gone from every Core API answer while a temporal query by type still finds its history. The kept rows go with the history. Delete Temporal Evolution removes them at once, and the retention sweep removes them once `temporal.storage.retention` has deleted the last of the history. An entity without a Temporal Evolution loses every row when it's deleted.

## Collation

Every text column whose comparison decides NGSI-LD behaviour is declared `COLLATE "C"` when it's created. That covers identifiers, dictionary names, `datasetId`, and the string and URI values of attributes. Comparison on those columns is byte by byte, whatever locale the PostgreSQL cluster was initialised with. Equality in `q` is therefore exact, and an `idPattern` that starts with a fixed prefix can use an index range.

Ordering is a separate decision. The ordering operators of `q` and `orderBy` compare strings by the Unicode Collation Algorithm, under the ICU root collation unless the request names another. Every query that orders strings names that collation itself, so the answer doesn't depend on the server's default, and the broker's in-memory evaluation of subscriptions follows the same rule.

Because each column fixes its own collation, a tenant database is created without one. A database default would decide nothing the specification defines.

The trigram indexes are the one place the database default is named. A pattern that leaves the start of its subject open (`name~="Nám\. Ľ.*"`, `idPattern=.*:0123.*`) is answered by a trigram index over the column. `pg_trgm` takes the trigrams of the indexed strings under the database's default collation, whatever the column declares, but those of the pattern under the collation the test runs under. Under `C`, in a database whose default treats `Č` or `Ž` as letters, the two disagree and the index loses strings the pattern matches. So each trigram index column is declared `collate "default"`, and a pattern it answers is tested under the default. The pattern means the same under every collation, because the broker restates it with every class written out as code-point ranges. A pattern that fixes its start (`idPattern=^urn:ngsi-ld:Sensor:.*`) is tested under `C`, which is what lets PostgreSQL read it as a range of the identifier B-tree.

[SQL lint rules](sql-lint-rules.md) describes the `c-collation` rule that holds every migration to this.

## Reading a page of Entities

An Entity query whose `q` holds conjuncts an index answers reads their candidates through the index and cuts the page from them. A conjunct may be an equality with one value on an Attribute's own value or on a sub-Property, a pattern, an ordering or a range over a number, a `DateTime`, a `Date` or a `Time`, the existence of an Attribute, or a Linked Entity hop. An equality on an Attribute's own value reads one branch per place the value can be held, each through its own index: the typed column the value's kind is stored in, and the containment keys of a structured value. PostgreSQL reads an equality with `false` as the negated column, from which it can't prove the predicate of the partial index over booleans, so that comparison states the column is not null.

The page tries each way in turn, behind a gate on what the ways before it found. A short walk probes the first 1 000 Entities of the selection in page order, which fills a page of a hundred for a term one Entity in ten holds, so a common term never reads its candidates: those of an equality 100 000 of 500 000 Entities hold come from a bitmap of all of them, 15 to 20 ms for 10 000 of them, where the short walk costs about 1.7 ms when it falls short. Then each keyed conjunct is read, at most 10 000 candidates of it, and the page is cut from the selection narrowed to the first conjunct's candidates that stay within that bound. A conjunct whose Attribute the census counts within the bound is read alone, the smallest count first, because its candidates always do. Otherwise the conjuncts are read in the order of the filter's normal form, so every spelling of one filter is read the same way and renders one statement, and a common conjunct read first costs only its bounded read before a rarer one answers. When every read passes the bound, a full walk probes the selection in page order. A Linked Entity hop's candidates are read whole, so no conjunct is read after a hop and its page has no full walk. The census is read only when two conjuncts contend, in one statement after the name dictionaries.

Left to plan these branches, PostgreSQL misjudges them in two ways. It takes the number of candidates from the bound, so narrowing the selection with `IN` over them hashes a scan of the whole selection even for a few dozen. The page narrows with `= ANY` over an array of them instead, which looks each one up by its key. Given a filter it believes rare, it reads every match through the filter's index, hashes them against the whole selection and sorts them before it cuts the page, however soon the page would fill: among 500 000 Entities a term 50 000 of them hold, spread through the selection, cuts its page in 84 ms that way and in 3 ms walked. Both walks therefore read the selection in page order as a subquery, fenced by its `LIMIT` or by `OFFSET 0`, and probe each Entity it yields in a lateral subquery fenced by `OFFSET 0`, which PostgreSQL can't turn into a join. The probe reads the Entity's own Attribute rows by its key and tests their value as one boolean test, `(...) IS TRUE`, which no value index answers. Given a value it believes rare, PostgreSQL would otherwise read the value's index on every probe and keep the Entity's rows afterwards, so each probe reads every row holding the value, 11.6 µs per Entity among 100 000 for an equality 50 of them hold, where the key reads it in 1.7 µs. A walk whose selectors or sort keys read the search row looks that row up for each Entity the same way, since joined plainly the full walk, planned to yield every row, becomes a merge join of every Entity with every search row sorted by identifier, 343 ms among 500 000 Entities before the first probe. Every filter of a walk but its selectors is tested on each Entity the walk yields the same way too, through a search row it looks up for itself and outside the walk's `LIMIT`, so the short walk visits its length of the selection whatever the filters keep. As a filter of the walk, the standing instance `attrs` reads becomes a semi-join over every carrier of the Attribute, which sorts every Entity by identifier in 946 ms, so a keyed page beside `attrs` takes 757 to 817 ms that way and 45 ms tested per Entity. Tested inside the `LIMIT`, a filter few Entities pass makes the short walk read the whole selection before it falls short.

The bound trades two placements of the matches, which no count tells apart before the read. Matches holding the last identifiers of the selection make the walk probe nearly every Entity: among 500 000 Entities that takes 0.3 to 0.9 s, where the index answers 10 000 such matches in 8 to 22 ms. Matches spread through the selection fill the page soon into the walk, in 7 to 22 ms for a term one Entity in a hundred holds and in 2 to 3 ms for one in ten, so a term most Entities hold walks on every page, after reading the bound's candidates. Reading 10 000 of them costs about 6 ms from a value index, whether an equality or a range reads it, and 28 ms as the carriers of an Attribute, while 50 000 cost 30 to 42 ms, which would put every page of a common term past 30 ms. A pattern whose trigrams most values share gathers every posting before its first candidate, 70 to 150 ms, and costs about 500 ms read in full, against 0.9 s for a walk past matches at the end of the selection. A bound derived from the size of the selection serves one placement only at the other's cost, so the bound is fixed, and the same for every kind of index read.

A page selected by `attrs` alone, or by an `idPattern` that leaves the identifier's start open, is gated the same way and makes the same trade. Its short walk visits 5 000 Entities, because a visit there costs a single index probe, a quarter to half a microsecond, rather than a probe of the Entity's attribute rows. The carriers of an Attribute are read up to 50 000 of them, since such a page reads them only for an Attribute too rare to fill the short walk. The matches of an `idPattern` are read up to 1 000, since a pattern whose trigrams most identifiers share costs more read through the index than walked: 5 000 matches spread through 500 000 Entities take 340 ms read and 9 ms walked.

A page filtered by a geo-query is gated the same way when it has no `orderBy`, no keyed term in `q` and no total to carry on its rows. The plain page reads every match of the geo-query through the spatial index before it cuts the first row, which among 500 000 Entities takes 0.8 to 1.0 s for a geo-query nearly all of them meet and 122 ms for one a tenth of them meet. Its short walk probes 200 Entities, each looked up by its key for an instance that meets the geo-query at about a microsecond apiece, so a broad geo-query fills its page in 0.4 ms. Its matches are then read up to 10 000 of them, about 7 ms through the spatial index, so a geo-query a tenth of the Entities meet reads them and walks in 8.3 ms. The walks read the membership of the requested types when the request selects by type alone, and `entities` otherwise. A rare geo-query pays for the short walk and a costlier plan before its matches answer, 0.8 ms against 0.5 ms for 111 matches, and one a hundredth of the Entities meet costs what the plain page costs. A counted page whose rows can carry the total stays plain, since counting the whole selection costs about what that page costs, 0.8 to 1.0 s for a broad geo-query, and a gated page would only add itself to the count. A keyed term in `q` keeps the keyed page, which reads the geo-query the same way ahead of its keyed conjuncts. Its walks read the membership the same way and probe each Entity for `q` and the geo-query, its matches are read first, at most 10 000 of them, and each keyed conjunct's branch then tests the geo-query on each candidate by its key, as its count does. Tested as the set of every match, the geo-query is hashed whole for the walks and read whole however few the candidates, and the short walk visits every Entity when the matches are few, so among 500 000 Entities `status=="fail"` (100 000 holders) beside a geo-query 111 meet takes 1 050 ms that way and 3.3 ms read this way, and `temperature>39.99` (47) beside one all of them meet 974 ms against 5.8 ms. The matches come first because a read that passes its bound costs its bound's candidates, 4.5 to 20 ms for the matches against 6 to 28 ms for a keyed conjunct and 70 to 150 ms for a broad pattern, so the slowest of these pages takes 40 ms read that way and 54 ms read the other way.

The filters a walk tests on each Entity it yields, `attrs` and `scopeQ`, are read as well, since when no other read answers, such a filter few Entities pass makes the full walk visit the whole selection. Among 500 000 Entities that each carry a Scope, a common keyed term beside a `scopeQ` none of them matches takes 633 ms walked, the Scope pattern tested on each Entity at about a microsecond, and 1.4 ms read. The keyed page and the geo page read the filter after the geo matches and before the keyed conjuncts. The carriers of `attrs` are read when the census counts at most 10 000 instances of its Attributes together, counted in the same statement as the contended conjuncts when the query names `attrs` beside a keyed term or a geo-query. Every carrier holds an instance, so the read then holds every carrier and answers, and only a Linked Entity hop's whole read follows it, so a page with a hop still never walks. Read past the census, 25 000 carriers cost 9 to 20 ms more than the walk. A keyed conjunct the census fits to its bound answers the same way, so beside it the page reads no filter. A `scopeQ` has no count, so its matches are read, at most 10 001 of them, through the partial index over the scope paths for a selective Scope and by a sequential scan for one nearly every Entity holds. A read that passes the bound costs 2.5 ms when nearly every Entity matches and about 11 ms for a Scope a tenth of them hold. Read after the geo matches, a Scope 5 000 Entities hold costs 0.8 ms beside a geo-query 111 of them meet, against 16.6 ms read before them. Read before the keyed conjuncts, a selective Scope beside a common term answers in 1.4 ms, against 13.7 ms after the conjunct's bounded read, and a rare conjunct beside a Scope thousands of Entities hold pays the Scope's branch instead, 31.9 ms against 1.2 ms for 5 000 of them. Projected members are tested on each Entity with no read.

A counted query whose page can't carry its total counts the matches in a statement of its own, reading the same conjuncts in the same order and counting from the first whose candidates stay within the count's bound of 10 000. A count needs every match. Walked, it costs the plan PostgreSQL makes of the whole filter, which reads the term's index itself for a term it believes rare and probes every Entity for one it does not. Among 500 000 Entities the index counts 10 000 matches in 5 to 50 ms where the walk takes 12 to 690 ms, and stays the cheaper way up to 50 000 matches, a tenth of the selection, except for a pattern whose trigrams most values share: its index gathers every posting, 350 to 500 ms, which an `idPattern` walks in about 250 ms. A count past the bound pays for the candidates it read before the walk, too little to tell apart from the walk when a value index yields them, about 20 ms as the carriers of an Attribute and up to 175 ms for a pattern whose trigrams most values share. Every count of a term most Entities hold takes that path, so the bound stays at 10 000. A page cut by its full walk passed the bound the count reads, so its total is counted by walking straight away.

A page judges every Entity and Attribute instance it reads at one instant (clause 4.22). A request's page reads at the transaction's `NOW()`. A periodic notification pages its candidates through the same statements with the instant its tick took bound in place of `NOW()`, so every page of its walk, each continued after the last identifier of the one before, and the evaluation in memory that follows decide expiry at that instant on one clock.

## Spatial

Geometries are PostGIS values in WGS 84, with GiST indexes on each entity's `location`, on the geometry values of attribute instances and on the geometries of registrations. The database checks that a stored geometry is in WGS 84 and is flat or three-dimensional.

Each broker process can also keep an in-memory index of entity locations, which narrows a geo-query on `location` before PostgreSQL runs it. It can only add candidates, and PostgreSQL checks every candidate against the full geo-query, so the answer is the same with it or without it. It names at most 64 candidates, which PostgreSQL looks up one by one, and stops looking at the 65th, since past a few dozen PostgreSQL's own spatial index reads fewer rows. Collecting every match of a geo-query 500 000 Entities meet would cost about 200 ms before the statement runs. A request that names its Entities by identifier is answered by no other, so the index names and counts only those, and a counted page of two Sensors within all the data reads them alone where it would otherwise read every match.

A gated page reads a geo-query two more ways. Its matches are read through the spatial indexes on their own, at most 10 001 rows of them, one per matching instance and in no order, and the page is narrowed to them. A walk probes each Entity it visits by its key instead, the default `location` through the search row's primary key and every other instance through the Entity's attribute rows. The probe tests each box without its spatial index, since an indexable box test lets PostgreSQL add a spatial index scan to every per-Entity lookup, and it reads no in-memory narrowing, which can only add candidates. A keyed page tests each candidate of its keyed conjuncts with the same probe, and so does its count. Both read the same instances with the same expiry test as the filter of the plain page, so each way of reading gives the same answer.

## Temporal

History is the `attribute_history` table, a TimescaleDB hypertable partitioned by recording time into chunks of `temporal.storage.chunk_interval`, seven days by default. A changed interval is applied when the tenant next opens. Temporal queries and aggregation read it, never the current-state tables. With the TSL edition of TimescaleDB, the broker itself converts chunks older than `temporal.storage.columnstore.convert_after` (30 days by default) to TimescaleDB's compressed column store. The broker also drops chunks past the retention age itself, and it creates no TimescaleDB job, so it needs no TimescaleDB background worker. The PostgreSQL image sets `timescaledb.max_background_workers` to 0 by default, which spares every tenant database a scheduler process of its own, and a server run otherwise can do the same. The image's `TS_TUNE_MAX_BG_WORKERS` sets them for a server that runs TimescaleDB jobs of its own: `off` (the default, also `0`), `tune` for the 16 `timescaledb-tune` gives, or a number of workers. The image sizes `max_worker_processes` as those workers plus the CPUs plus 3. The history of each entity's Scope, `scope_history`, is an ordinary table.

Aggregation runs over the raw hypertable for each request, not over a continuous aggregate. A continuous aggregate has to bucket on the partition column, `recorded_at`, and clause 5.2.21 admits no such Temporal Property, so a materialised aggregate would answer a question the API cannot ask.

### The activity horizon

Each Temporal Evolution has an activity horizon, `evolution_active_until` on its `entities` row. It's an upper bound on every instant the Evolution's attribute instances hold on any time axis (`observedAt`, `createdAt`, `modifiedAt` and `deletedAt`), rounded up to the end of the UTC hour. Every statement that writes an instant into the history raises it to cover that instant. That includes Modify Attribute Instance, since clause 5.6.14 lets the replacement declare any `observedAt`. Nothing lowers the horizon while the Evolution lasts. After Delete Attribute Instance, or a retention sweep that keeps the Evolution, the horizon can stay above what the history still holds, which only makes the Evolution a candidate that the query then rejects. Delete Temporal Evolution, and the retention sweep's removal of an emptied Evolution, clear it along with the Evolution's other columns.

The statement that creates an Evolution's `entities` row also writes its horizon. A Core API create that records its history in the same transaction stamps the horizon of its acceptance instant, which every entry it records carries as `createdAt` and `modifiedAt`. The Temporal API, creating an Evolution its Entity didn't have, stamps the horizon its entries reach. The history recorded right after then finds the horizon in place and leaves the row alone. Raising it there would change an indexed column, so it couldn't be a heap-only update. It would leave a dead version of the row in the heap and an entry in every index on `entities`, including the trigram index over `id`, which takes about a hundred keys for a long identifier. A create whose `observedAt` lies in a later hour is still raised by its history. An Entity created without attributes has no horizon until its first attribute instance.

A temporal query with `timerel=after` or `between` reads its candidates from the horizon. An instance inside the window is at or after the window's start, so every Evolution the query can keep has a horizon at or after the start. The candidates are therefore the Evolutions written within the hour before the start or later, read by a range scan of the horizon index. Entities whose history stopped earlier, like the many deleted Entities whose Temporal Evolution a Core API delete leaves standing (clause 5.6.6), are never read. A `before` window reaches back without limit, so no horizon narrows it. The hour rounding is what keeps this cheap on the write path. A write changes the indexed column only when it moves the horizon into a later hour, which happens about once an hour for an Entity written steadily, and every other write stays a heap-only update of `entities`.

### Ordering the writes of one Entity

A write of an Entity's current state is never stamped earlier than an instant the Entity already holds (clause 4.8). The `entities` row holds all three such instants, `modified_at`, `evolution_modified_at` and `deleted_or_queued_at`. The third holds the instants the other two can't. A core deletion clears `modified_at`, and its tombstones state no type, so they leave `evolution_modified_at` as it was. A queued write's history reaches `evolution_modified_at` only when the drain applies it. So the deletion and every enqueue raise `deleted_or_queued_at` in their own transaction, under the row lock, and a write compares against the greatest of the three on the row it writes or locks. Under READ COMMITTED that row is the latest committed version, whereas a subquery over the queue would read the statement's snapshot and miss an intent committed while the statement waited on the row. The column isn't indexed, so its update stays heap-only.

A commit that writes more than one Entity locks every existing identity row it writes before any of its writes run. It locks them in identifier order, which is byte order, the `C` collation that both `entities.id` and the queue's `entity_id` declare. It takes `FOR UPDATE` when it deletes any of them, and `FOR NO KEY UPDATE` otherwise. The lock is needed because the commit's statements reach their rows in submission order, while the drain locks every identity row of a batch `FOR NO KEY UPDATE`, in identifier order, before its first statement. Locks taken in two orders deadlock. PostgreSQL would break each cycle only after `deadlock_timeout`, by rolling back one side, and a drain that loses falls back to one transaction per intent.

The drain's lock also orders it against a Temporal Evolution deletion, which takes `FOR UPDATE` on the row before it removes the streams, the history and the Evolution. Applying an intent reads whether the Entity holds an Evolution before it gives it a stream or history. Without the row lock, a statement whose snapshot predates the deletion's commit would give a stream to the Evolution the deletion gave up. Every later intent that states types would then bring the Evolution into being again and insert that stream again, which the grain's unique constraint refuses.

A commit that writes one Entity takes no such lock, since it holds one row and waits on no other. A write that records history without changing current state writes no row, so the commit locks its row in the same statement before its history is placed, and the probe for queued history and the intent keys follow commit order for it too. The lock reads the row's version, and the write is held to the version it states. A Temporal Evolution backfill folded against a current state that a concurrent write replaced, a deletion included, records nothing and is folded again. After a deletion it therefore brings the Entity into being again, instead of adding history the fold no longer describes.

A core deletion keeps the identity row while the Entity holds a Temporal Evolution or `deleted_or_queued_at` is set. So an Entity whose history is still queued keeps a row that holds neither a current state nor an Evolution. The drain brings the Evolution into being on that row, and a later create of the identifier lands on it and is held after the deletion. A fresh row would be compared with nothing, and could take on the history of the Entity the deletion removed.

Giving up the Temporal Evolution (clause 5.6.16, or retention) keeps the row while it holds a current state, or while an intent of the Entity is still queued. A row kept by its current state clears the column unless such an intent waits, because the current state's `modifiedAt` already follows every earlier deletion and the history the drained writes left is gone. A row kept for its queue alone keeps the column, and only the retention sweep leaves one. A deletion queued behind the Evolution it gave up is a later write, and a create of the identifier is held after that deletion when it lands on the row.

A Temporal Evolution deletion leaves no queue behind. Reads count queued history as recorded, and clause 5.6.16 removes all of it, so under the row lock the deletion removes every queued intent of the Entity instead of applying them first. That leaves the state that applying them and then deleting would leave, reached in one transaction, whether or not a queued write could still apply. An Evolution that queued history alone brought into being is given up the same way. On the live branch, giving an Evolution up counts a row holding the column as holding one, so once its intents are gone, the row is either removed or keeps its current state with the column cleared. The statement reads the queue after the caller has locked the row in a statement of its own, so it sees every intent committed before, and no writer queues more until the caller commits. A deletion of an Entity with neither an Evolution nor queued history therefore removes its row.

No Snapshot branch holds such a row. A capture writes every Entity it captures through the store's own writes, from the current state and history that the live branch's readers serve, and those readers skip a row that holds neither. A clone copies the published branch of another Snapshot, never the live branch. A Snapshot branch has no queue, so its deletions keep a row only for an Evolution, and giving the Evolution up there clears the column.

### Reading a page of history

The statement that cuts a candidate page keeps one generic plan per connection. Each of its branches reads one access path, whatever the request binds. The short walk and the full walk probe each Evolution in identifier order, and the candidates come from the step's own index (the horizon, the identifier trigrams, the Scope paths or the stream extents). The Scope paths index is partial, and a generic plan uses a partial index only when the statement's text implies its predicate, so the read states the predicate as a literal. Bound as a value, the predicate would leave the plan reading every Scope row, 68 ms among 1 000 000 Evolutions where the index answers a page of 500 matching rows in 2 ms. A plan made with the bound values would choose nothing different that matters, and planning a statement of three history reads costs about a millisecond, several times its execution. It runs without parallel workers, since a `Gather` under a branch whose gate fails still launches its workers. A page that needs more matches than the short walk visits can't be filled there, so its statement holds no short walk, and its candidates decide alone between the candidate branch and the full walk.

Each step's bounds trade the two placements of the matches, as a page of Entities does. A short walk fills the page for a term about one Evolution in ten answers, one in two for a geo-query, whose short walk is 50 Evolutions, and one in 250 for an `idPattern`, whose short walk is 5 000, and it costs a fraction of a millisecond to 3 ms when it falls short. Past its bound the page walks, which is quick for matches spread through identifier order and probes every Evolution for matches that hold the last identifiers. Among 1 000 000 Evolutions, 20 000 such matches walk in 0.22 s for an `idPattern`, 0.7 s for a `scopeQ` and 5 s for a geo-query or a window, against 26 to 120 ms read in full. A window has one more way. When the short walk's matches project the page full within 1 500 Evolutions, it walks without reading the candidates, which pays among 1 000 000 Evolutions (11 ms against 32 ms for a window one Evolution in a hundred answers) and loses among 100 000 (10 ms against 7 ms), since the walk to the page costs the same at every size while the candidates grow with the selection.

A stage 1 count reads at most 10 000 candidates before it walks. Both ways test every Evolution they count against the window, and a broad window matches by a semi-join over the history of every stream, so among 1 000 000 Evolutions counting the candidates takes 0.7 to 2.2 s and walking 1.6 to 4.7 s. The index stays cheaper until the candidates are about seven in ten of the walk. Reading every candidate would count the terms between the bound and a fifth of the selection 1.3 to 5.5 times faster, but counts a Scope that seven in ten Evolutions hold a twentieth slower, so the bound is fixed.

Once the candidates are cut to a page, the history of every Entity on it is read in one statement, and its Scope events in one more. The identifiers are bound as one array, and each Entity is read in a `LATERAL` over it, its streams through their own indexes, as a read of one Entity would be. The per-Entity read ends in `OFFSET 0`, so PostgreSQL runs it once per identifier. If it were pulled up into the outer join, the planner might read every stream of the branch, and run each stream's page read, before dropping the Entities the page doesn't name. A page therefore costs the same statements whatever its size, each one round trip and one planning. The rows come back ordered by Entity and are decoded one Entity at a time, so an Entity whose stored history doesn't read back drops from the response with a warning while the rest of the page answers. The aggregated representation is read the same way.

An aggregated page holds at most `temporal.query.max_last_n` periods per stream. It finds where it stops by a skip-scan over the stream's axis index, one probe per period that holds an instance. When the window is bounded at both ends and the period has a fixed length (days and time, no years or months), the window overlaps at most ⌈span / period⌉ + 1 periods. When that number, plus one for the rounding of a fractional period, fits within the page, the period count can never end the page. The read then takes only the first probe, which the instance bound still needs, instead of walking every period of the window.

### Index direction

The direction of each history B-tree follows how PostgreSQL splits a full leaf. When a key is no wider than two eight-byte columns and a new entry lands at the end of a run sharing its leading column, the split is made at the new entry and the left page stays full. Otherwise the page is halved, and the half that receives no further entries stays half empty.

Every history row a write records, through the Core API or the Temporal API, holds the write instant on `createdAt` and `modifiedAt`, and Modify Attribute Instance moves only `modifiedAt`, to the instant of the modification. Each stream therefore receives both instants in increasing order, so `(stream_key, created_at)` and `(stream_key, modified_at)` ascend. Measured on PostgreSQL 18 with 2.5 million rows per chunk, the ascending key is 41% smaller at 10,000 rows per stream, 15% smaller at 1,000, and within 2% at 300 or at 10. Around 100 rows per stream, a run shorter than one leaf, it's up to 7% larger. A cached `lastN` reads the ascending index backward and costs about 2% more.

The entity-led `scope_history` keys descend. A Scope changes rarely, so an Entity holds few events, where the direction leaves the size unchanged, and every read of them is a head lookup that a descending key answers with a forward scan.

The `observedAt` and `deletedAt` keys add the write's identity as tie-breakers, its write id and the row's ordinal within the write, and leave the write instant out. Write ids come from one version 7 counter per broker process, which keeps rising when the clock steps back, and a write mints its id after the read its compare-and-set is checked against. So a stream's rows tied on an instant sort by write id, in the order their writes committed. The identity makes those keys too wide for the split at the new entry, so their size is the same in both directions. They descend, the order a `lastN` reads, because a backward scan of an ascending key costs a `lastN` 5 to 7%.

## Disk space

A table gives back no disk space on its own. Vacuum turns removed rows into free space inside the table's pages, which only new rows of the same table reuse. So a work queue that a burst filled and that then drained, or a `current_attributes` thinned out by deletions, keeps its size. History chunks are different. Past the retention horizon they are dropped whole, and converting a chunk to the columnstore rewrites it compactly. For the other tables, the maintenance controller measures the free space of each table and its TOAST table and, once it has lasted, repacks the table online through `pg_repack`, which copies the rows into new files and swaps them in. [Online repack](online-repack.md) describes how it decides and how a run proceeds.

## The context source change clock

`context_source_change_clock` is one row per tenant database that orders the writes of context source registrations against the writes of context source subscriptions. Every create, update and deletion of a registration, every expiry sweep over them, and every client write of a context source subscription advances its revision in its own transaction, after every lock another write could hold. The row lock that advance takes is held until the transaction ends, so the revisions follow the order the writes commit in, and a registration change is matched only against the subscriptions written before it. The advance is the last statement of each write, and it reaches the server in one message together with the transaction's `COMMIT`. The server runs the two back to back, so the row is held for the advance and the commit's flush only, never while an answer travels back to the broker and its `COMMIT` travels out again, a round trip every write queued on the row would otherwise wait out once more. A context source subscription draws its revision the same way, in a last statement that writes the drawn revision onto the subscription's row. Until then a newly created subscription carries the latest revision committed before it, which no reader can see, since the commit that makes the row visible replaces it. A write waiting on that lock holds one of the tenant's pool connections, so these writes begin their transactions through a share of the pool of their own. It admits as many of them at once as `database.write_reserve_percent` keeps from read requests, and at least one, while read requests hold at most the rest of the pool beside that reserve. However many writes queue on the row, they hold no more of the pool than that, so they alone never exhaust it. Waiting for a place in the share counts toward `database.acquire_timeout` like waiting for a connection, so a write that finds neither in time is answered 503 with `Retry-After`. The share only bounds how much of the pool the queue holds. The row lock still orders the revisions.

## Registrations a write is forwarded to

`registration_information` holds one row per `EntityInfo` of a registration, and every distributed write reads its candidate registrations through those rows' indexes. A single-entity write names its entity's identifier and type. A batch write names every identifier of its array and every type its entities carry, in one statement, so it reads the registrations that could match one of its entities and no others. A batch deletion carries no types and is matched on its identifiers alone. Each registration that statement returns is then matched entity by entity, as clause 5.12 describes. A batch write in a tenant that holds no registration reads none at all. The broker counts each tenant's registrations as the tenant opens, those past their `expiresAt` that the expiry sweep has not deleted yet included, adds a creation before it reaches the database and takes a deletion away once it has committed. A write whose outcome is unknown stays counted, so the count can exceed what the database holds but never falls short of it.

## Subscription copies at context sources

A Subscription that takes part in distributed operations has a reduced copy at each matching registration's context source, and `forwarded_subscriptions` records each copy with the identifier it carries there. The broker records a copy before it sends it, because a source may notify under the copy the moment it holds it, and a notification under an identifier the broker doesn't know is refused for good. In the same transaction it writes a claim to `forwarded_subscription_claims`, which holds the instant the placement's lease ends, and the source's answer settles the copy by deleting the claim. An acceptance settles it, and so does an `AlreadyExists`, which says the source holds the copy already. Any other error status from the source removes the record and its claim, except on a claim taken over, as described below. A forward that got no answer keeps both under the lease, since the source may hold the copy, and so does a gateway's 502 or 504, which says the source behind it gave no valid answer in time. A 504 naming `LdContextNotAvailable` is the source's own refusal (Table 6.3.2-1 of ETSI GS CIM 009 v1.9.1), not a gateway's. A placement can be cut off between the record and the answer by the request deadline, a shutdown or a crash. The lease, twice the request deadline, outlasts every placement still under way, so a claim past its lease was abandoned. The next placement of the same copy takes the claim over and sends the copy again under the identifier recorded, and a background pass of each tenant does the same for every abandoned claim, except that it withdraws the copy from a registration that takes no copy any more, being auxiliary or no longer advertising the creation of subscriptions. A forward that never reaches the source, held back by a cooldown or refused at the connection, removes a claim recorded with the copy, since nothing was sent before it. On a claim taken over it learns nothing of what an earlier send left there, and neither does an error status that depends on the moment the request came (408, 429, 500 or 503), so both keep the record and the claim to the lease and a later pass tries again. Only a source refusing the copy as sent removes a claim taken over, since it refused the earlier send too, and one holding the copy would answer `AlreadyExists`. The tenant's earliest obligation includes the earliest lease end, so the pass runs, and wakes a tenant nobody is using, only when a claim is due. A source that already holds the copy answers it with `AlreadyExists`, so it never holds two.

## Posted queries

A query sent by POST (clauses 6.23.3.1 and 6.24.3.1) is paged like any other query, and each page link has to be a target a client "could dereference" (clause 6.3.10). A URL can't carry the body, and the POST binding exists because long URLs get cut on their way to the broker. So when a POST answer has a neighbouring page, the broker keeps the query in `posted_queries`, and the link is a GET on `/entities` or `/temporal/entities` that names the kept row by its digest in `postedQuery`, beside the POST's own URL parameters and the paging parameters. A page that has no neighbour keeps nothing.

The digest is the SHA-256 of the operation (entities or temporal), the query document and the @context it was read under, cut to 16 bytes and held as those bytes, which a page link spells as 22 base64url characters. Posting the same query under the same @context again lands on the same row, so it answers the same links and only pushes `expires_at` back. A query-string walk over a compiled query digests into `pageQuery` the canonical identity record of the compiled query (a JSON object built from the normal form of each filter and the expanded selectors, so `q=a==1;b==2` and `q=b==2;a==1` are one walk), then the decoded, sorted pairs of the selection parameters the identity does not carry, and a collection with no compiled query digests its sorted selection pairs alone, from an even number of parts. A posted query is digested from three parts, the first of which is an operation name, which the identity record, a JSON object, is never, so the kinds of digest never collide. A cursor taken from a posted walk is bound to the digest in the same way a query-string cursor is bound to its `pageQuery`.

The row holds the query as its JSON document and the @context either as the IRI of the `Link` header or as the body's `@context` member. Following a link reads the row and runs the query as the POST did, forwarding it to context sources as a batch query in the same way. A selection parameter beside the digest, or a request whose @context differs from the kept one, gets `BadRequestData` (clause 5.5.9.1). A follower that sends no @context reads under the kept one.

`posted_query.lifetime`, one hour by default, sets `expires_at` from the last POST, and following a link doesn't extend it. A row past `expires_at` is never read, and the expiry sweep deletes it every `expiry.sweep_interval`. `posted_query.quota` caps the rows and the bytes one tenant keeps (10,000 rows and 256 MiB by default), because any client that may read can fill the table. Every write takes one transaction-scoped advisory lock first, ranks the rows from the latest `expires_at` to the earliest, and evicts those past either cap, so the rows expiring soonest go first and the row it has just written never does. An evicted or expired digest gets `BadRequestData` like a digest that was never issued, and posting the query again issues it anew.

## Snapshots

A Snapshot is a schema of its own inside the tenant's database, with its own copy of the entities, their history and the subscriptions. The same migrations build the live tables and every Snapshot's copy, so a Snapshot is read with the same queries as the live data.

## Migrations

The broker carries its migrations and applies them itself. They come in three sets.

- The platform set runs in the platform database.
- The tenant set runs in every tenant database, the platform database included, since it holds the default tenant. In a tenant's live schema, the tenant migrator runs the tenant and branch files together, in version order.
- The branch set runs on its own inside every Snapshot's schema. It builds the schema when the Snapshot is created, and the schema then takes every later branch migration together with the live schema.

Each migrator records what it applied in its own ledger table (`_andromeda_tenant_migrations` for the tenant and branch files of a tenant, `_andromeda_branch_migrations` in a Snapshot schema), with the checksum of every file, and refuses a database where an applied migration was edited or is missing. Every tenant database is also stamped with its schema version and a digest of the tenant and branch migrations that built it. A broker migrates a tenant whose stamp is behind and advances the stamp, once the applied ledger rows digest to the value the stamp claims. It refuses to serve a tenant whose digest differs at the same version, whose stamp is ahead of its own, or whose ledger doesn't confirm the stamp, so a stale or foreign database can't be used by accident.

A tenant database is at one schema version, in every schema it holds. Every branch, the live one and each Snapshot's, stores values of the composite types the live schema owns, and a migration that changes such a type changes the values every branch holds at once. So the broker walks the tenant set in version order, and a branch migration runs in the live schema and then in every Snapshot's schema before any later migration runs anywhere. Each migration commits in each schema in a transaction of its own, so the walk never holds the locks of every Snapshot at once. The walk is decided from what the ledgers record. A run cut short anywhere, by a crash or a lost connection, resumes where it stopped the next time the tenant opens, and a Snapshot that missed a branch migration takes it before anything else runs. The stamp is written only once every schema has come through, so a stamped tenant holds no Snapshot behind it, and opening a current tenant reads nothing of its Snapshots.

A Snapshot schema that cannot take a migration stops the walk, and the tenant doesn't open. The error names the Snapshot, its schema, the migration the walk was bringing it through and the migration that failed. The migration that failed leaves nothing behind, and the Snapshot keeps the migrations it took before that one. The walk resumes the next time the tenant opens, once the schema has been repaired or the Snapshot's row in `snapshots` deleted, which leaves its schema to the expiry sweep to drop. A schema no row of `snapshots` names is never migrated. The platform database is migrated when the broker starts, so a Snapshot of the default tenant that cannot take a migration keeps the broker from starting.

A migration that a stable release has sealed never changes, so from then on the schema only grows by new migrations. A migration no release has sealed yet is still edited in place, which means a newer build can refuse a database an older build created. [Migration sealing](migration-sealing.md) describes the contract, and [SQL tooling](sql-tooling.md) the tool that keeps the migrations in shape.

## Tenant template

Migrating an empty database through the tenant set takes about 300 ms of server time, and copying a database that's already migrated takes about 50 ms. So the broker keeps a migrated database locked as a template, and every new named tenant's database is a copy of it.

The template is `template_` followed by `tenancy.databases.name_prefix`, so `template_andromeda_tenant` by default, beside PostgreSQL's own `template0` and `template1`. Each broker has a template of its own, and two brokers sharing a server under different prefixes never touch each other's. A tenant database name ends in an underscore and a digest of the tenant's name, so no tenant database is named like a template unless a prefix itself ends in such a digest.

The broker brings the template to its own schema every time it starts, before it serves, the way it brings a tenant database forward when the tenant opens. It unlocks the template, updates its extensions to the versions the server ships, runs the migrations it lacks and stamps it, then locks it again. When the template is current this takes a few milliseconds. A broker started on a fresh platform database, or on one v1.0.0 left, finds no template and builds one, and a later release brings that template forward in place. When the template holds a schema the broker can't bring forward, such as a stamp ahead of the broker after a downgrade, another migration set at the same version, or a migration that fails, the broker drops it and builds it again and logs `tenant_template_rebuilt`.

A locked template refuses connections. On a server that runs TimescaleDB background workers, TimescaleDB keeps a scheduler session connected to every database that holds the extension and admits connections, and a database with a connected session can't be copied. The broker locks the template first and then stops its scheduler from a session it opened before the lock, so no scheduler can attach in between, and from then on TimescaleDB doesn't schedule the template again, a server restart included. A start cut short while the template is unlocked leaves it unlocked, and the next start locks it. Fleet maintenance skips a locked template, and `pg_dumpall` leaves it out of a dump, which costs nothing since the broker builds it again when it next starts.

The template is a cache and never decides a schema. A copy is migrated like any new tenant database, so a copy of a template behind the migrations is brought forward by them, and every copy gets a schema stamp instant of its own. A tenant database that already exists, whichever release created it, is migrated where it stands and never replaced, and opening an existing tenant never touches the template.

When the template can't be prepared, for example because the broker's role may not stop the TimescaleDB scheduler, the broker logs `tenant_template_unavailable` and creates every new tenant's database empty and migrates it. A copy that fails because the template has gone missing, or because a session still holds it once the retries are spent, falls back the same way for that one database and logs `tenant_template_not_copied`. To remove a template by hand, stop the broker, run `ALTER DATABASE ... WITH IS_TEMPLATE false` on it, then drop it.

Creating, dropping, locking and unlocking a database run on a connection that waits a bounded time for each lock and has no statement timeout. `DROP DATABASE` waits for a checkpoint, and on a server writing many databases at once that checkpoint takes longer than the statement timeout the broker sets for requests.
