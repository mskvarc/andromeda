# SQL lint rules

`andromeda-sql lint` runs Squawk over the migrations first, then Andromeda's own rules, which cover the conventions the schema depends on that Squawk can't express. These rules read the schema the migrations declare from PostgreSQL's own syntax tree and token scan, through the `pg_query` crate. They also read the two `pg_format` vocabulary files and the seal ledger, which tells them which migrations a release has already shipped. They never read Rust. A check that compares a migration with a Rust constant is a test in the `andromeda-sql` package, not a lint. Every finding names its rule along with the file, line and column, and any finding fails the run. Sealed migrations are read as part of the schema, but no finding is reported in them, since they can't change and the finding could never be fixed.

No migration can turn a rule off, whether it's one of these or one of Squawk's. If a rule needs an exception, the rule changes, and its exceptions are data in the rule's own module, each with a name and a reason. That's also why `.squawk.toml` turns off Squawk's `adding-foreign-key-constraint` and `constraint-missing-not-valid`. Neither can tell a live table from one created earlier in the same unreleased migrations, which is still empty when it deploys, unless the migration carries an inline suppression. `constraint-on-sealed-table` below takes their place, because it reads the seal ledger and knows which tables a release has shipped. Squawk's `prefer-bigint-over-int` and `prefer-bigint-over-smallint` are off too, because `integer-width` below decides integer width with knowledge of the schema they don't have.

## Storage and collation

`lz4-compression` requires every column of a type PostgreSQL can compress to declare `compression lz4` in `create table` or `alter table ... add column`, or to get it from an `alter table ... alter column ... set compression lz4` later in the same migration. Squawk can't parse `compression` inside `add column`, so an added column gets its method from a separate `set compression` statement. The rule decides from the declared type whether a column is compressible. That covers the variable-length types it knows (`text`, `json`, `jsonb`, `bytea`, `numeric`, `bit`, the PostGIS and `ltree` types and the like), arrays of known types, every composite type a migration creates, and every domain over one of these. A type the rule doesn't know, `inet` or `xml` for example, isn't checked, and neither is a column retyped with `alter column ... type`. A composite type field takes no compression clause, whether `create type` declares it or `alter type ... add attribute` adds it, so the rule doesn't check it. The clause only picks the algorithm. PostgreSQL compresses a value only once its row grows past about 2 kB, so short values pay nothing for it. lz4 compresses nearly twice as fast as the default pglz and decompresses faster, at the cost of slightly larger output. Naming it on each column also keeps the choice away from the server's `default_toast_compression`, which a migration must not set.

`c-collation` requires every column, composite type field and domain of a collatable type (`text` and its kin, and arrays of them) to declare `collate "C"`. The same goes for every `alter column ... type` to such a type, because retyping a column without it resets the column to the database default. No other collation appears in any `collate` in a migration, so no index element overrides a column's `C`, with one exception. The key of a trigram operator class (`gin_trgm_ops`, `gist_trgm_ops`) names `"default"`. `pg_trgm` takes an indexed string's trigrams under the database's default collation, and a pattern's trigrams under the collation the pattern test runs with. Under `C`, the pattern's trigrams would leave out the non-ASCII letters the default collation recognises, and the index would miss strings the pattern matches. The key stores nothing, and every trigram match is checked again anyway.

The specification leaves no room for any other stored collation. String equality compares code units (ETSI GS CIM 009 v1.9.1 clause 4.9, which refers to IETF RFC 8259 section 8.3), and temporal `min` and `max` are lexicographic (Table 4.5.19.1-1). In UTF-8 both come down to byte order. The only place a collation gets chosen is when a response is ordered, per request (Table 5.2.43-1), and the query names it. With `C` on every stored text value, the database's default collation decides nothing, and an upgrade of the operating system's collation library can't corrupt an index.

`integer-width` allows a 32-bit `integer` column or composite type field only for values that can't outgrow it. Those are a key of a name dictionary or a reference to one, an ordinal of something an instance holds, a schema version, a server process id (`backend_pid`, which PostgreSQL itself types as `integer`), and a counter on the bounded-counter list that a check keeps at zero or above. The name patterns for each kind are data in the rule. Every other integer is a `bigint`. A `smallint` table column is a code or a small count, so a check has to bound it, unless it's a catalogue identifier assigned outside the database (`unit_code_id`). Composite type fields, including those `alter type ... add attribute` adds, can't carry a check, so their `smallint`s are bounded on the table columns they're written to. An array is judged by its element type. A column retyped with `alter column ... type` isn't checked.

`key-length-bound` requires every text column a B-tree keys, through a primary key, a unique constraint or a B-tree index, to carry a check `octet_length(column) <= n` with `n` no more than 2,704 bytes. PostgreSQL refuses a B-tree entry larger than that with SQLSTATE 54000 at insert time. An unbounded text key is a write waiting to fail on a long value, and a bound above the limit lets in values the index then refuses.

`fixed-width-before-variable` keeps fixed-width columns ahead of variable-length ones in every table, with added columns counting as last. PostgreSQL caches the offset of each column up to the first variable-length one, and has to find any fixed-width column after that by walking the row on every read. Composite types are exempt, because their fields follow the order of the table columns they're written to.

## References and placement

`set-isolation` limits each migration to the relations its own set can reach where it runs. The platform set runs only on the platform database and references only platform relations. The tenant and branch sets run in every tenant database and never reference a platform relation. Without this rule, a test against the default tenant would pass, since its database holds both, while every named tenant failed. The branch set also runs alone inside every Snapshot schema, so it references only relations a branch migration creates, plus the types and functions in `public`, which its search path reaches. It creates no type, domain or extension, because that would live in that one schema. It also declares no foreign key into a tenant relation, because deleting a Snapshot could then wait on a lock in the live branch.

`foreign-key-indexed` requires the referencing columns of every foreign key to lead the table's primary key, a unique constraint or an index without a predicate. They can lead it in any order, an index of any method counts, and only plain column keys are read, not expressions. When a row in the referenced table is deleted or its key changes, PostgreSQL looks up the referencing rows by those columns. Without such an index, that lookup scans the whole referencing table while the referenced row stays locked. References into the append-only dictionaries `attribute_names` and `entity_type_names` are exempt, listed as data in the rule. Their rows are never deleted or rekeyed, so the lookup never happens.

`hypertable-shape` requires a table passed to `create_hypertable` to have no foreign key in either direction and no unique key without its partition column. TimescaleDB refuses a foreign key into a hypertable and a unique index without the partition column. A foreign key out of a hypertable is checked chunk by chunk, and it stops retention from dropping a chunk.

`constraint-on-sealed-table` covers a foreign key or check that `alter table` adds to a table a sealed migration created. The constraint has to be named, added `not valid`, and validated with `validate constraint` in a later migration. A sealed table may already hold rows on every installation. Adding the constraint directly checks all of them under the `access exclusive` lock that `alter table` takes, which blocks every read and write for as long as the table scan runs. With `not valid`, the lock lasts only a moment and only new rows are checked. `validate constraint` then checks the existing rows under a lock that lets reads and writes carry on, and with it in a migration of its own, the two locks never share a transaction. A table created by a migration that isn't sealed yet is still empty when its release deploys, so adding a constraint to it costs nothing and the rule lets it through. A hypertable is the exception the other way round. TimescaleDB refuses `validate constraint` on a hypertable whose columnstore is enabled, and the broker enables it while it runs, so a constraint added `not valid` to a hypertable could never be validated. The rule requires a constraint on a sealed hypertable to be added validated, in one statement that checks the rows its uncompressed chunks hold. A check that restates one its table already held is the last case. Dropping a column drops every check that names it, and the check added again without the column holds for every row that met the one it replaces. Reading the table to add it would learn nothing, and on `attribute_history` that read is the whole of the history not yet in the columnstore, in the live schema and in every Snapshot's. So the rule requires such a check to be added `not valid` and asks for no later validation, on a hypertable as on any other table. PostgreSQL still tests every row written after that against it, and a chunk created later holds it validated. The checks are listed as data in the rule, which names `chk_attribute_history_tombstone_members`.

`heap-only-columns` keeps the columns that change on almost every write of their row out of every index key, expression, predicate and `include` list. Their updates then stay heap-only and don't touch any index. The list is data in the rule. It holds an Entity's `modified_at` and `evolution_modified_at`, the `times_sent` and `times_failed` counters of the two delivery-state tables, and the `claimed_by` column of five claimed queues, `notification_deliveries`, `snapshot_preparation`, `snapshot_notification_outbox`, `pending_side_effects` and `temporal_append_intents`. A queue's `lease_until` sets its claim order and is indexed on purpose.

`index-hygiene` makes three checks. No index uses `text_pattern_ops`, `varchar_pattern_ops` or `bpchar_pattern_ops`, which order text byte by byte for anchored patterns, as the `C` collation already does. No index expression or predicate calls a function whose name starts with `hash`, which catches the built-in hash functions, because a major release may change their values and silently invalidate the index. And when two non-unique indexes on one table share a method and predicate, and the keys of one lead the keys of the other, the shorter one goes. If both have the same keys, the later one goes. The longer one serves every query the shorter one does, and the shorter one costs an extra index write for every row.

## Functions

`function-body-bound` requires every `language sql` function to have a SQL-standard body (`return ...` or `begin atomic ... end`) instead of a string. A string body is parsed the first time a session calls the function, using that session's search path. `pg_dump` restores with an empty search path, and since PostgreSQL 17 maintenance commands run with `pg_catalog, pg_temp`, so a stored generated column computed through such a function fails to restore. A standard body is parsed and bound once, when the function is created.

A PL/pgSQL function is always parsed late, so it names every relation with its schema. A trigger that reaches the branch relation of the schema it fires in builds its command with `format('... %I.relation ...', tg_table_schema)`, and the rule reads that by expanding the template. An `execute` whose command isn't built by `format` with a constant template is a finding, and so is a `%I` bound to anything but `tg_table_schema`, because the rule can't tell which schema it names. An embedded statement that doesn't parse is a finding too. Transition tables a trigger declares are exempt, because the trigger names them and no schema does. The PL/pgSQL tree comes from PostgreSQL's own PL/pgSQL parser. Its tree writer produces invalid JSON for the implicit variables of a trigger function, so the rule reads a trigger function through a stand-in that returns `integer` and has the same statements and expressions. The parser reads a body without the catalogue, so it takes every type it doesn't know for `record` and an array of one for `record[]`, a pseudo-type PL/pgSQL refuses for a parameter, a result and a variable alike. A PL/pgSQL routine that takes, returns or holds an array of a composite type therefore carries it inside a composite, as `sub_attribute_tree` carries the elements of one attribute instance's sub-attributes. A body the parser refuses stops the run with an error naming the migration, because no rule can read the schema without it.

`no-or-replace` forbids creating any object with `or replace`. A migration runs once against a schema the earlier migrations built, so it has nothing of its own to replace. `or replace` would silently overwrite an object with the same signature that something else created first.

`no-catch-all-exception` forbids exception handlers that catch `others`, in a function or in a `do` block. A handler that skips one expected failure that way swallows every other failure too, a real installation error included, and the migration then succeeds without having done anything. Instead, a block checks first for what it needs, against `pg_available_extensions` for example, or catches only the condition it expects.

`no-security-definer` forbids `security definer` functions, in `create function` and in `alter function`. Such a function lends its owner's privileges to every caller, which gets around the grants the operator set up. A body that resolves names through the caller's search path can also be steered into running some other object as the owner.

## Text

`lowercase` forbids uppercase letters in code tokens. That covers keywords, identifiers, operators, numbers and literal prefixes such as `B'0'`, inside function bodies too. `pg_format` lowercases only the words it knows, so everything else keeps whatever case it was typed in. Comments, the contents of string constants and quoted identifiers such as `"C"` are text and keep their case.

`formatter-vocabulary` checks that `pg_format` knows every function a migration calls, including the `execute function` target of a trigger, and that some migration uses every word in `.pg_format_functions` and `.pg_format_keywords`. `pg_format` lays out a call of a function it knows as `name(` and a call of one it doesn't know as `name (`, so the canonical layout depends on its vocabulary. The rule asks the pinned `pg_format` itself which functions it knows, in one run over a statement that calls each name once, so the answer follows the release rather than a copied list. Calls inside a function body don't count, because function statements are kept away from `pg_format`. Calls inside a `do` block do count, because `pg_format` formats those.

`identifier-length` requires every identifier a migration writes to fit in the 63 bytes PostgreSQL keeps. PostgreSQL cuts a longer one short without an error, so two names that differ only after the limit collide, and the name the code uses no longer matches the catalogue. The parser reports the shortened name, so the rule reads identifiers as written from the token scan instead, which covers every kind of object and every reference.

`comment-style` sets the header every migration opens with. The header is a rule line of `-- ` and 76 `=`, then `-- NNNN: Title` with `NNNN` the file's own version and no full stop, then another rule line, the comment lines, and a closing rule line. A `-- Spec:` line among the comment lines always has the form `-- Spec: ETSI GS CIM 009 v1.9.1 clause ...`. The title line is the only comment that may carry a migration number, and the rules on what a comment may cite don't apply to it. A released migration is frozen, so no other comment may point at anything that can move. That rules out code (`::`, `.rs`, `crates/`, `andromeda-`), documents (`docs/`), working records (`Wave`) and other migrations by number. Every line holding a comment fits in 80 columns, counting any code before the comment, and holds no ` -- ` dash, no `TODO` or `FIXME`, and no `squawk-ignore`, because no migration turns a rule off. The rule finds comments through the token scan, so a double hyphen inside a string constant isn't taken for one.

## Naming

`object-prefix` makes the name of every constraint, index and statistics object start with the prefix for its kind (`pk`, `uq`, `fk`, `chk`, `ex`, `idx`, `uq` again for a unique index, `stx`), followed by its table's name part. The name part is the table's registered abbreviation when it has one (`ca` for `current_attributes`, `csr` for `context_source_registrations`, `pse` for `pending_side_effects`), and its full name otherwise. A table with an abbreviation is never spelt out in an object name. The name alone then tells you what an object is and which table it belongs to, and every object of a table uses the same spelling. An unnamed constraint breaks the rule, because the name the server makes up follows no convention.

`forbidden-word` keeps unregistered abbreviations (`attr`, `db`) out of names, along with words that describe how a value is stored instead of what it means (`uuid`, `geo`, `bool`, `datetime`). Table and column names spell out even registered abbreviations. Columns that keep a specification member's name (`geo_q`, `local_only` and the like) are exempt, listed as data in the rules.

`bound-suffix` forbids naming a constraint `_bound`. A check that bounds a size is named `_length`, the one word every size check uses.

`claim-index-suffix` requires an index whose name has a word starting with `claim` to end in `_claim`, so every claim index can be found under one name.

`write-identity-suffix` names a unique constraint over a write's `write_id` `_write_identity`, which is how a replayed write is recognised.

`identity-not-key` names a column the database generates as an identity `_key`, the word for a surrogate the database assigns.

`integer-identifier-not-key` keeps the names `id` and `_id` for integers assigned outside the database, which are listed as data in the rule. An integer the database generates is a `_key`.

`identifier-array-not-keys` forbids naming an `integer[]` or `bigint[]` column `_ids`. An array of database-generated integers is named `_keys`.

`foreign-key-column-name` names a referencing column after the column it references, either alone or behind the role it plays. A reference to an `id` is `<what>_id`, and a table holding two subscriptions names them `local_subscription_key` and `companion_subscription_key`. A join then reads as the same name on both sides.

`boolean-not-predicate` names a boolean column as a predicate, `is_<what>`, unless it's a value column (`value_...`), the key of a one-row table (`singleton`), or keeps a specification member's name.

`trigger-name` names a trigger `trg_<table>_<what>` after the table it fires on, using the same name part as `object-prefix`. That's the registered abbreviation when the table has one, and the full name otherwise.
