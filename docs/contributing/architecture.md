# Architecture

Andromeda is a Cargo workspace of about 80 library crates under `crates/`, two tools under `tools/`, and the broker binary at the root. Each crate owns one responsibility. This page describes how the crates fit together and the rules that keep them that way.

Many of the rules are enforced by `andromeda-architecture-checks`, whose gates run as ordinary tests in `cargo test --workspace`. They read the workspace's manifests and its Rust source as a syntax tree, the way the compiler sees it. Each enforced rule below names its gate, so a failing gate leads back to the rule behind it. A rule written down only decays, because someone crosses it in a hurry and nobody notices. A rule that runs as a test fails the moment it's crossed, and whoever crossed it has to fix the code or change the rule in the open.

## Where code goes

### The workspace

Dependencies point one way. Transport and persistence depend on the domain services, the services depend on the NGSI-LD model, and nothing depends back up. `andromeda-broker-composition` is the only crate that sees every layer.

- **NGSI-LD model.** The `andromeda-ngsi-ld-*` crates hold the specification's typed values and resources and do everything that needs no I/O. `ngsi-ld-lexicon` has the validated value types, `ngsi-ld-model` the resources built on them, and the rest cover JSON-LD expansion and compaction, the query language, request parameters, rendering and problem details.
- **Domain services.** `andromeda-entity`, `andromeda-temporal`, `andromeda-subscription`, `andromeda-registration`, `andromeda-federation`, `andromeda-notification`, `andromeda-snapshot` and their neighbours make the broker's decisions. They reach storage through ports they define, and none of them names a database driver.
- **Persistence.** The `andromeda-postgresql-*` crates implement those ports on PostgreSQL. All SQL is spelled in `andromeda-postgresql-seaquery` and nowhere else (gate `raw_sql`).
- **Transport.** The `andromeda-http-*` crates turn requests into calls on the domain services and render what comes back. `andromeda-http-server`, `andromeda-http3-server` and `andromeda-server-tls` run the listeners.
- **Shared foundations.** Small crates any layer may use, such as `andromeda-json-literal`, `andromeda-jsonld`, `andromeda-retry`, `andromeda-telemetry`, `andromeda-tenancy` and `andromeda-configuration`.
- **Wiring.** `andromeda-broker-composition` builds each tenant from the configuration and connects the layers. The `andromeda` binary depends only on it and on `andromeda-configuration`.

Almost every crate has a dependency contract, a test generated by the `dependency_boundary!` macro. It lists the workspace crates the crate may depend on and the third-party crates it must not ship, such as a database driver, an HTTP framework or the async runtime, and fails when the crate's `Cargo.toml` says otherwise, dev-dependencies included (gate `dependency_boundary`). Adding a dependency therefore means editing the contract, where a reviewer sees the new edge. The contract is also where `anyhow` and other banned crates are refused. Many crates, every HTTP crate among them, also carry a `forbid_sql!` test, which fails on any SQL fragment in their source.

### Layers

Domain logic stays out of transport, persistence and API code, and they stay out of it. A function or type that crosses a layer boundary without a deliberate abstraction is wrong, however many lines it saves. Each crate and each module owns exactly one responsibility and has a small, clear public API. Code in the wrong layer is a bug, not a matter of style.

### Configuration

`andromeda-configuration` owns every configuration section, its mode enums and its defaults, and it depends on no other workspace crate (gate `configuration_layering`). A domain crate takes only the section it reads, never the root `BrokerConfig`. The conversion from a section into domain types lives in the domain crate, and the broker composition runs those conversions while the configuration loads (gate `configuration_ownership`).

Every configuration type, key and choice has an operator-facing description in `#[schemars(description = "...")]`, kept separate from its rustdoc (gate `configuration_description`). Every comparison the validator runs is a declared `Rule`. The configuration template, JSON Schema and descriptor are generated from all of this and checked in. [Getting started](getting-started.md) shows how to regenerate them.

### Ownership rules

- **Backend crates never depend on each other.** A crate named for one storage backend never depends on a crate named for another. A concept two backends share lives in a neutrally named crate that both depend on.
- **One engine per cross-API concern.** A concern that spans several APIs, such as the scope grammar or Linked Entity retrieval, has exactly one engine, and every consumer runs it. A consumer supplies only the I/O (a source port) and the spelling (a representation adapter), and it makes none of the concern's decisions. The gates `scope_grammar`, `linked_retrieval`, `registration_matching` and `time_handling` each fail when a decision is taken outside its engine.
- **A failure is classified once.** The NGSI-LD problem a broker failure is reported as is chosen in `andromeda-failure-classification`, which names no transport. That choice covers the clause 5.5.2 type or clause 6.3.17 status, the detail a client may read, and how soon a retryable failure may be repeated. The HTTP bindings answer with it, and a Snapshot records it in the execution result of the query that met the failure. An HTTP crate adds only the request instance and the `Retry-After` header.
- **History is written atomically.** An entity mutation and the temporal history rows it produces commit in the same database transaction. There is no asynchronous recorder and no post-commit hook.
- **Stored and exchanged formats stay standard.** A standard format is never stored in a non-standard shape to save cost. GeoProperty values, for example, are never stored as `@json` literals to get them past the JSON-LD processor. When a representation is expensive, make the in-memory model cheaper instead.
- **Repository mappers live in the repository.** The conversion from a domain type into repository parameters sits beside the parameter struct in the repository layer, or the repository takes the domain type directly. A service never does it.
- **Renderers own every transformation.** A handler configures a renderer through its builder and calls `render()`. It never calls a transformation itself or edits the rendered output.
- **Crate bans are architecture checks.** A rule that bans a crate or confines it to one owner crate is a gate in `andromeda-architecture-checks`, not an entry in `deny.toml`.

### No duplication

When two places need the same functionality, it moves into the module that owns the concept. When two crates need it, it becomes a library crate of its own under `crates/`. Code is never copied between crates or modules.

## What the gates catch

The gates below run over the whole workspace. Most of them check production code only, not tests, build scripts or test-only items. `time_handling` reads test code too, because a test that parses a time some other way asserts behaviour the broker doesn't have, and so do `module_naming` and the part of `raw_sql` that looks for statement text handed to the driver. Some gates have a baseline, which tolerates only the entries listed on it and can only shrink. Today only the `type_erased_error` baseline has an entry, a single one for the DNS resolver in `andromeda-outbound-http`, because `reqwest`'s `Resolve` trait hands errors back boxed. So every other gate fails on the first violation.

| Gate | Fails on | Why |
|---|---|---|
| `raw_sql` | SQL spelled, or statement text handed to the driver, outside `andromeda-postgresql-seaquery` | Every other crate holds statements as values, so no query is hand-written into a domain or HTTP crate. |
| `untyped_json` | a `serde_json::Value` tree, `json!` or a conversion into one | A general JSON tree allocates per node, loses member order and can be made arbitrarily deep. [Type design](type-design.md#json) lists the three forms JSON may take. |
| `type_erased_error`, `string_typed_error` | a `dyn Error` trait object, or an error variant holding a `format!` message or a flattened source | An error keeps its structure until it's logged, so a caller can still tell one fault from another. |
| `detail_message` | a client-facing message that breaks the wording rules in [Rust style](rust-style.md#errors) | Two of those rules can't be expressed as types. |
| `swallowed_row_decode` | a column that fails to decode being read as zero, empty or absent | Answering from a default would answer as if nothing were wrong. |
| `state_codec_boundary` | a PostgreSQL crate turning entity state into a JSON document | PostgreSQL holds entity state as typed rows. |
| `scope_grammar`, `linked_retrieval`, `registration_matching`, `time_handling` | a decision of that concern taken outside its one engine | Two readings of the same rule let one endpoint accept what another refuses. |
| `geometry_box_test` | a geo-query box test on a bare geometry column | A long great-circle edge bows past its vertices, so the box has to be the one the spatial index keys. |
| `raw_constant` | an IRI or media type kept as a plain string constant | A constant is validated when it compiles. |
| `configuration_layering`, `configuration_ownership`, `configuration_description` | the configuration rules above | |
| `god_file`, `module_naming` | the file size and module name rules below | |
| `comment_hygiene` | a spaced `--` or an em or en dash in any comment, or a `clone:` note in test code or one that points at another line or names a shared handle | A comment states a reason in words of its own, with commas, colons or parentheses in place of dash asides. |
| `manifest_hygiene`, `package_metadata` | the manifest rules in [Dependencies](dependencies.md) | |

The same tests also refuse `pub use` re-exports, the identifiers and paths of retired architecture (such as `AppState`), and any implementation of `FromRequest`, `FromRequestParts`, `Header` or `IntoResponse` outside `andromeda-http-extraction`, `andromeda-http-headers` and `andromeda-http-response`. Paths qualified more than they need to be are caught by the `clippy::absolute_paths` and `unused_qualifications` lints instead.

## How big it gets

### Files

A module file holds one cohesive concept, which is one type and its impls or a family of closely related small types. When a file starts to host a second concern, that concern moves to its own file straight away.

Not counting `#[cfg(test)]` code, a file past about 400 lines should be split, and a file past 600 lines must be (gate `god_file`).

A module's name says what it owns. These names describe nothing and are not allowed (gate `module_naming`).

- `utils.rs`
- `helpers.rs`
- `common.rs`
- `shared.rs`
- `misc.rs`
- `core.rs`
- `types.rs`

### Structs, traits and functions

- A struct models one concept and holds only what that concept owns. Don't pass a bag-of-everything struct around so callees can reach whatever they need. A function takes the specific values it uses.
- A struct whose fields fall into clusters that never interact is really two or three structs.
- A trait declares one capability, so no implementor has to stub half its methods.
- A function does one thing at one level of abstraction. Extract the phases of a multi-phase function into named functions.

The test is reasons to change. If two parts of a file, type or function change for unrelated reasons, they belong apart.

## How it changes

### Changing an API

Changing an API means changing every consumer of it in the same pull request, until the whole workspace compiles without warnings. Nothing keeps the old shape alive, and these rules have no exceptions.

- No `pub use` re-exports of any kind, including preludes and facade modules, so every import names the module that defines the item (enforced by the architecture checks).
- No shims, adapters, bridges or compatibility layers that keep an old API working.
- No deprecated aliases, forwarding wrappers or type aliases that keep an old name.
- No legacy or compatibility code paths, and no feature flags or `cfg` branches that keep an obsolete path reachable.
- No fallbacks that silently accept an old field name, variant or wire format. Shapes the NGSI-LD specification requires a broker to accept are features, not shims, and they stay.
- No defaulting or `unwrap_or` to paper over a mismatch between two APIs.

Delete dead and commented-out code, since git keeps the history. If a complete migration looks impossible, raise it in the issue before you write a workaround.
